## 2. CR-01 交接预约卡 —— Rejected

- **原提案**：批准后生成结构化交接卡（时间段、校内公共地点、备注），双方可改可确认，完成后归档并随争议导出。
- **必要性评估**：中。现有匿名聊天已能约定时间地点，卡片主要提升可追溯性，不是阻断性缺口。
- **影响面评估**：大。需要新增共享记录与版本冲突处理、归档与导出格式、多端一致性；会突破已稳定的“申请 + 会话 + 交接码”数据与流程边界。
- **估算**：2–3 人日（估算，未实测）。
- **裁决**：本轮 **Rejected**，作为未来候选保留，不进入 V1.1。
- **重提条件**：真实用户反馈“约见信息散落导致爽约”占比较高；且愿意承担共享记录的并发编辑与导出改造。
- **不做的影响**：争议导出仍只含会话文本；约见信息继续以聊天文本存在。可接受。

## 3. CR-02 驳回后冷静期 —— Rejected

- **原提案**：同一申请人对同一记录，被驳回后 24 小时内不得再提交；拾获方可“允许重申”提前解除。
- **必要性评估**：中。反骚扰价值存在，但会阻碍“补齐证据后立刻重申”的正当场景。
- **影响面评估**：中。需新增拾获方权限入口、时间边界、并发与提示文案；属于规则与权限变化，不是纯前端。
- **估算**：1–2 人日（估算，未实测）。
- **裁决**：本轮 **Rejected**。不把它描述为已实现或已确认的需求。
- **重提条件**：需要真实涉众（申请人、拾获方）对“冷静期是否公平”明确表态；并接受为学生裁决项，而非工程默认。
- **不做的影响**：被驳回后可立即重申，骚扰风险仍在。接受，记录为已知限制。

## 4. CR-03 认领列表分组 —— Accepted（Revised）

**采纳理由**：必要性高、影响面小；`GET /v1/claims` 已支持 `role=applicant|finder` 且返回 `total`，无需数据库、状态或认证变更。

**精化要求（Revised，实施必须逐条满足）**：

1. 默认进入“我发起的”；另一组为“我收到的”；两组各自显示**准确** `total`。
2. 移除混合视图入口；**API 的 `role=all` 仍保留**以兼容旧调用，服务端不改。
3. 切换分组、刷新、切换身份时，列表与计数同步更新；计数读取失败显示“—/暂不可用”，**不得显示 0**。
4. 同一条申请不得在两个分组中重复计数；组内保留角色标签、分页与空组说明。
5. 服务端权限不变：分组只是呈现与默认筛选，越权仍由服务端 403 拦截。

**实施边界**：
- 只改前端三文件：`web/index.html`、`web/styles.css`、`web/app.js`。
- 无数据库、状态机、认证、DTO/接口 schema 变更。
- 回滚 = 回退这三个文件。

**状态**：`Accepted-PendingVerification`。前端会话实施后，由测试回填实际 UI 验证记录；在回填前，
本文与 RTM 都不声称已验证。

## 5. 本轮不做的事

1. 不重跑后端全套性能：CR-03 不改后端，重复全套压测没有信息增量（若前端引入额外请求风暴，另行评估）。
2. 不改匹配规则、评测集或标签。
3. 不宣称 CR-01/CR-02 已实现；也不把 Rejected 写成“以后一定做”。

## 6. 风险与开放问题

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 计数与列表不同步 | 快速切组时旧请求晚到，可能覆盖新组数据 | 请求带分组标记，忽略过期响应 |
| 计数失败被显示为 0 | 会误导“没有待办” | 统一占位“—/暂不可用” |
| 双计 | 同一 claim 同时满足两个条件 | 以 `claim.id` 去重后再计数 |
| 身份切换残留 | 上一身份的私有列表短暂可见 | 切换即清空并重新拉取，禁止跨身份缓存 |
| 服务端 `role=all` 被误删 | 破坏兼容 | 明确写进验收：该参数保留 |
